Install Android to a virtual disk

The VM window is open. Do the 6 steps below once; afterwards ApkStart boots straight from the disk and no image is needed.

  1. Boot menu: use ↓ to select Installation - Install Android-x86 to harddisk, press Enter
  2. Choose Partition: choose Create/Modify partitions; when asked about GPT choose No
  3. cfdisk partitioning: New → Primary → press Enter to accept the size → Bootable → Write → type yes → Quit
  4. Format: choose vda1 → when prompted to format choose ext4 → Yes
  5. Bootloader & system: Install GRUB choose Yes; Install /system as read-write choose Yes
  6. Done: when it reaches 100%, click "I've finished installing" below (ApkStart restarts and takes over automatically)

If adb later reports not connected: in the VM window press Ctrl+Alt+F1 to open a terminal, run setprop service.adb.tcp.port 5555, stop adbd, start adbd, then press Ctrl+Alt+F7 to return to the graphical interface.

App window
Press F11 or right-click the tray icon to switch; fullscreen only enlarges the window and keeps the aspect ratio — switching does not restart the app.
In window mode you can drag the border to resize; this sets Android's internal render size — smaller is faster.
Mouse mapping
The emulator natively treats left click as a finger tap and press-drag as a swipe; nothing to configure.
By default the emulator also treats right click as a tap (easy to hit by mistake). When enabled, right click only triggers Back.
Smooth mode merges a short burst of wheel events into a single swipe gesture, avoiding tick-by-tick stutter and one adb process per tick.
Side-button mapping needs a global mouse hook. The hook is installed only while an ApkStart app window is in the foreground and removed immediately on focus loss or close, so the desktop is unaffected.
These mappings apply only while an app window is in the foreground; back on the desktop or after closing the window, the mouse behaves exactly like native Windows.
Performance & resources
Controls how much CPU the Android VM uses and how sharp the picture is. Switch to "Smooth" when video apps stutter, "Low power" to just leave small apps running. Takes effect the next time you open an app.
Expansion happens in place: installed apps and saves are kept; the next app launch just takes a few extra seconds.

Assigns public Chinese DNS (Alibaba / Tencent) to Android. By default Android uses the host's DNS, which can add hundreds of ms when the host is on a VPN or corporate network, slowing the first screen of video apps. Turn off if intranet domains misbehave.
Plays app notification sounds and video audio. Turn off only if you don't need sound and want to save a little CPU.
The second launch of an app takes only seconds, at the cost of an extra ~2–3 GB ram.bin on disk. Can be turned off when space is tight: it only affects launch speed, not apps or saves.
Container details (advanced)
Caps the vCPU quota and lowers process priority so the Windows desktop gets CPU first. The "Resource policy" above already sets this automatically.
Game mode keeps the Android VM at a higher CPU priority and reduces host-side polling, minimizing input and display latency; the rest of the machine may slow down. With no app window open the container still parks at low priority.
Also disables background packages such as Play Store, Setup Wizard and print services, keeping only what's needed to run apps. If an app complains about missing Google Play services, turning this off restores them automatically.
After ApkStart starts, the Android environment boots in the background with the window fully hidden (you never see the emulator). Opening any app then costs only the "open" step — measured from 20+ seconds to almost no wait. The trade-off is ~1 GB of RAM while idle; with this off the first app launch is a cold boot.
The Android environment boots once and stays resident; opening an app no longer restarts the whole system, it just starts that app and stops the others. Closing the last window clears the background and parks the container; the next open is still instant.
Downloads & update source
"Auto" asks both GitHub and Gitee for the latest version, downloads 256 KB from each candidate URL to measure speed, then downloads from the fastest one; one unreachable source doesn't block updates.
When direct GitHub is slow, also benchmark the public forwarders ghfast.top / gh-proxy.com (they only forward public release files, no accounts involved). When off, only direct connections and your own prefix are used.
When filled, only your prefix is used and the two public mirrors above are skipped; when empty, the "Auto" logic decides. The downloader prepends it to the real URL.
Large files are downloaded in parallel chunks. The default 8 threads already saturate most home connections; try 16 on a stable network.
Gitee update source (optional)
This repository is public and Gitee's release list can be read anonymously, so leaving this empty works. Only needed if Gitee rate-limits you (403/429) or you want to read a private branch: gitee.com → Settings → Private token, tick only "projects"; it is used solely to read the release list and uploads nothing.
